# OpenWiki Server — 解决方案（MVP）

> 状态：设计方案 v1（2026-08-19）；**MVP 已落地（M0–M5 完成，M6/I1–I3 待 open-ikc 侧集成）**
> 范围：参考 `semantica-graph-server`（`graph_engine`）的分层与五面接口模式，把 LangChain **OpenWiki**（Node CLI，Markdown wiki 内核）封装为独立对外服务的 Wiki 引擎，供 `/home/open-ikc` 的 Wiki 库能力消费；
> 对外提供 **HTTP / gRPC / Celery / MCP / CLI** 五类接口；open-ikc 现有 wiki 对外接口（`tree / page / search` 与 parse 联动）基于引擎能力优化与调整。

## 1. 现状盘点

### 1.1 参考实现 semantica-graph-server

- 分层：`interfaces`（五面）→ `application.GraphEngineService`（用例，五面共用）→ `domain`（稳定 ID / schema / 合并）→ `persistence`（SQLite WAL）→ `adapters`（semantica 守卫式导入）。
- 统一协议：envelope `{traceId, errCode, errMsg, data}`，错误码 `0 / 200001 / 200404 / 200409 / 200500`，`X-Trace-Id` 透传。
- gRPC 用运行时动态 descriptor（离线无 `grpc-tools`），MCP 自研 stdio JSON-RPC，CLI 为 typer（退出码 0/1/6 对齐 open-ikc `ikc`）。
- job 登记 + Celery worker：`submit_job / run_job / get_job / list_jobs`，任务与 HTTP `async=true` 复用同一 application 层。

### 1.2 open-ikc Wiki 现状（占位实现）

- 形态：`kbMode=wiki` 专业库，`wikiConfig`（`granularity / extractFields / linkMode / dedup / template`）。
- 数据：进程内 dict（`app/services/wiki_store.py` `WikiPageStore`），无持久化。
- 稳定 ID：`pageId = wiki_ + sha1(kbId:stableKey)[:12]`，`stableKey = normalize_title(title)`。
- 接口：`GET /api/v1/knowledge-bases/{kb_id}/wiki/tree|page|search`，envelope 对齐；`parse` 成功后 `WikiService.build_from_doc` 联动建页（当前占位单页）。
- `process.md` 待办：真实解析/抽取引擎接入、`executeMode=async` 后台执行器、P4 `searchMode=page` 检索路由。

### 1.3 OpenWiki 内核（LangChain `langchain-ai/openwiki`）

- 形态：**Node.js CLI**（`npm install -g openwiki`），本机已有 Node v22.23.1 / npm 10.9.8；`openwiki` 未安装。
- 命令：`openwiki --init / --update`（code 模式）、`openwiki personal --init / --update`、`openwiki ingest <connector>`（git-repo / notion / web-search / hackernews / x / slack / gmail / 自定义 MCP）、`openwiki auth <provider>`、`openwiki visualize [dir] [--port] [--export]`。
- 产物：**OKF v0.2 Markdown 包**——概念页带 YAML front matter（`type / generated / tags / sources / status / stale_after`），`index.md / log.md` 为保留文档，概念页之间用标准 Markdown 链接表达互链，内嵌 Mermaid 图。
- 依赖：LLM provider（`OPENAI_API_KEY` 等）；code 模式会改写仓库根 `AGENTS.md / CLAUDE.md` 的 `<!-- OPENWIKI:START -->` 块。

### 1.4 结论

open-ikc 需要的是**独立、可持久化、可同步/异步调用的 Wiki 引擎**。当前占位实现的稳定 ID、dedup 合并、增量废弃、树/检索语义应完整迁移到引擎侧并保持一致，open-ikc 退化为薄客户端；引擎以 OpenWiki 为内核提供真实加工能力，LLM/网络不可用时规则模式降级（同 graph-engine 的 semantica 守卫式策略）。

## 2. 引擎总体设计

### 2.1 分层架构

```
┌────────────────────────────────────────────────────────────┐
│  interfaces（协议面）                                        │
│  HTTP(FastAPI) · gRPC(dynamic descriptor) · Celery ·       │
│  MCP(stdio JSON-RPC) · CLI(typer)                          │
├────────────────────────────────────────────────────────────┤
│  application：OpenWikiService（用例编排，五面共用同一逻辑）    │
├────────────────────────────────────────────────────────────┤
│  domain：WikiMeta/WikiPageRecord/稳定ID/wikiConfig校验/合并  │
├────────────────────────────────────────────────────────────┤
│  persistence：SQLite（wikis/pages/jobs）+ wiki 文件目录       │
│              （data/wikis/{wiki_id}/，OKF Markdown 为主存储）│
├────────────────────────────────────────────────────────────┤
│  adapters：openwiki（CLI 子进程适配，守卫式）                 │
│            + OKF 解析器 + 规则切页生成器（离线降级）           │
└────────────────────────────────────────────────────────────┘
```

### 2.2 关键语义映射（open-ikc wiki ↔ OpenWiki 内核）

| open-ikc 概念 | openwiki-server | OpenWiki 内核落地 |
| --- | --- | --- |
| 知识库 `kbId` | `WikiMeta`：`wiki_id = wiki_ + sha1(kbId)[:12]`，`root_dir = data/wikis/{wiki_id}/` | 每个 wiki 一个独立目录（等价 personal 模式实例） |
| `wikiConfig` | `domain/config.py` 校验与默认值 | `granularity` 驱动规则切页或 LLM 提示词；`template` 进 update 指令 |
| 页面 | `WikiPageRecord`：`pageId = wiki_ + sha1(kbId:stableKey)[:12]` | OKF 概念页（slug 文件名 + front matter `title/type/tags/sources/status`） |
| `fields` 结构化字段 | OKF front matter 扩展字段（`extractFields` 白名单） | LLM 合成或规则抽取后写 front matter |
| `links` 互链 | `links[]`（title + pageId） | 概念页 Markdown 链接解析 + `visualize --export` 的 `graph.json` |
| `sourceDocs` 证据 | `sources` front matter | OKF provenance 族（`sources`） |
| `status` 生命周期 | `active / deprecated` | front matter `status / stale_after` + 引擎增量废弃 |
| dedup | `merge / overwrite / skip` | `domain/merge.py`（对齐 open-ikc 现有语义） |
| 页面树 | `parentPageId / level` | 目录层级 + front matter 父页声明派生 |
| 检索 | 标题加权 > 正文，可 tag 过滤 | 引擎内建页面索引；OpenWiki `graph.json` 供可视化/邻接扩展 |

### 2.3 内核调用模式

- **MVP：CLI 子进程适配器**。`adapters/openwiki.py` 用 `subprocess` 调 `openwiki`：
  - `build_from_doc`：把文档写入 `{root_dir}/sources/{doc_id}.md` → 以独立目录跑 `openwiki personal --update`（或规则模式直接切页）→ 解析 OKF 输出入库；
  - `update`（全量刷新）：`openwiki personal --update`，env 注入 `OPENWIKI_PROVIDER / OPENWIKI_MODEL_ID` 与凭据；
  - `ingest`（连接器）：`openwiki ingest <connector>`，作为 Celery 异步任务；
  - `visualize`：`openwiki visualize {root_dir} --export {root_dir}/visualizer --no-open`，产出 `graph.json` 供树/可视化。
- **守卫式降级**：`openwiki_available()` 检测 `openwiki` 可执行文件；`OPENWIKI_SERVER_OPENWIKI_ENABLED=0` 或调用失败时切**规则模式**（按 `granularity=heading/section/page` 确定性切页 + 标题抽取），保证离线/无 LLM 全链路可用。
- **安全约束**：引擎只操作自己的 `data/wikis/{wiki_id}/` 独立目录，**绝不在 open-ikc 仓库根跑 code 模式**（避免改写其 `AGENTS.md / CLAUDE.md`）。
- **演进位**：定义 `WikiKernel` 接口，后续可用 Node bridge（stdio JSON-RPC 暴露 OpenWiki 程序化能力）替换 CLI 解析，避免 CLI 输出格式漂移。

## 3. 五类接口

### 3.1 HTTP（FastAPI，默认端口 18011，前缀 `/api/v1/wiki`，envelope 对齐 open-ikc）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/wikis` | 创建 wiki 实例（`kbId / wikiConfig / tenantId / ownerId`） |
| GET | `/wikis` | 列表（tenantId/ownerId 过滤） |
| GET/DELETE | `/wikis/{wiki_id}` | 详情 / 删除（级联删文件与库记录） |
| GET | `/wikis/{wiki_id}/tree` | 库级页面树（page/pageSize 分页） |
| GET | `/wikis/{wiki_id}/page` | 单页详情（markdown/fields/links/sourceDocs） |
| GET | `/wikis/{wiki_id}/search` | 页面检索（q + tag 过滤，评分排序） |
| GET | `/wikis/{wiki_id}/stat` | 统计（pageCount/tag 分布/linkCount） |
| GET | `/wikis/{wiki_id}/export` | 导出（jsonl/json/okf 目录包） |
| POST | `/wikis/{wiki_id}/build` | 按文档建页（docId/title/tags/markdown，`async=true` 登记 job） |
| POST | `/wikis/{wiki_id}/merge` | 显式页面记录增量合并 |
| POST | `/wikis/{wiki_id}/deprecate-doc` | 按 docId 增量废弃 |
| POST | `/wikis/{wiki_id}/update` | 全量 OpenWiki 刷新（LLM 合成） |
| POST | `/wikis/{wiki_id}/ingest` | 连接器摄取（git-repo/web-search/…） |
| POST/GET | `/jobs`、`/jobs/{job_id}` | 任务登记/查询（build/update/ingest/export） |
| GET | `/health` `/ready` | 存活/就绪 |

### 3.2 gRPC（`proto/wiki/v1/wiki.proto`，默认端口 50052）

- `WikiService`：`CreateWiki / GetWiki / DeleteWiki / ListWikis / BuildWiki / MergeRecords / DeprecateDoc / Tree / Page / Search / Stat / ExportWiki / UpdateWiki / Ingest / RunJob / GetJob`。
- 统一 `Envelope`（`trace_id/err_code/err_msg/data_json`），与 HTTP 语义一一对应；沿用动态 descriptor 实现（环境无 `grpc-tools`）。

### 3.3 Celery（broker/backend 默认 `redis://localhost:6379/0`，env 可覆盖）

- 任务：`openwiki_server.build / merge / deprecate_doc / export / update / ingest`，与 HTTP `async=true` 共用同一 application 层，返回 jobId。

### 3.4 MCP（stdio，`openwiki-server serve mcp`）

- 工具：`wiki_create / wiki_list / wiki_get / wiki_delete / wiki_tree / wiki_page / wiki_search / wiki_stat / wiki_export / wiki_build / wiki_merge / wiki_deprecate_doc / wiki_update / wiki_ingest / wiki_job_run / wiki_job_get`。

### 3.5 CLI（typer，`openwiki-server`，退出码 0/1/6 约定同 open-ikc `ikc`）

- `openwiki-server serve http|grpc|mcp|worker`
- `openwiki-server wiki create|list|get|delete|tree|page|search|stat|build|merge|export|deprecate-doc|update|ingest`
- `openwiki-server job list|get`

## 5. open-ikc 集成与接口优化

### 5.1 消费侧改造（薄客户端）

1. `app/services/wiki_store.py` 的进程内 `WikiPageStore` **替换**为 openwiki-server 客户端（HTTP/gRPC），`WikiService.tree/page/search/build_from_doc` 转发引擎；稳定 ID、dedup、deprecate 语义保持。
2. `parse` 成功联动：同步 `build`（小文档）或 `async=true` 登记引擎 job（对齐 `executeMode=async` 待办）；任务状态经 `wiki/jobs/{job_id}` 查询，parse 任务状态同步。
3. SDK：`sdk/python/open_ikc_sdk/models/wiki.py` 已有模型可复用；新增 `OpenWikiServerClient`（或 engine 前缀配置），MCP/CLI 工具覆盖新端点。
4. 部署：引擎独立服务（HTTP 18011 / gRPC 50052），`docker-compose.yml` 增加 `openwiki-server` 服务；open-ikc 环境变量 `OPENWIKI_SERVER_URL` 指向引擎。

### 5.2 wiki 对外接口优化点（基于 OpenWiki 能力）

| 优化项 | 现状 | 引擎落地后 |
| --- | --- | --- |
| 真实正文/fields | 占位文本、fields 空 | OKF 概念页真实正文 + front matter 字段（`extractFields`） |
| 切页粒度 | 恒单页 | `granularity=auto/heading/section/page` 规则切页；LLM 模式更强 |
| 互链 | links 空 | `linkMode=auto` 解析概念页互链 + `graph.json` 邻接 |
| 增量语义 | merge/overwrite/skip + deprecated 已具备 | 语义保持，持久化 + 跨构建稳定 |
| 检索 | 标题加权>正文（进程内） | 引擎索引 + 评分排序；为 P4 `searchMode=page` 路由提供后端 |
| 异步 | 无 worker | `async=true` 真实执行 + job 状态查询 |
| 可视化 | 无 | `visualize --export` 静态图（graph.json）可挂 Portal |
| 导出 | 无 | `export jsonl/json/okf`，对齐 download 产物流待办 |

### 5.3 遵守 open-ikc `AGENTS.md` 约束

- 不扩大能力面：wiki 仍是知识库形态（专业库）内的能力，引擎消费不新增第五类业务域；
- 不破坏统一协议：envelope / traceId / errCode 保持；错误码走 registry；
- 改路由必改 `catalog.py`；文档按权威顺序同步；任务开始/收尾更新 `process.md` 与 `docs/worklog.md`；
- 收尾自动 commit + push（用户明确不推时除外）。

## 7. 风险与对策

| 风险 | 对策 |
| --- | --- |
| OpenWiki 依赖 LLM/网络（无 key/离线） | 规则模式降级（granularity 切页 + 标题抽取），全链路离线可跑 |
| CLI 输出格式随版本漂移 | 锁定 openwiki 版本；OKF v0.2 为稳定契约；`WikiKernel` 接口预留 Node bridge |
| code 模式改写仓库 AGENTS.md | 引擎仅用独立目录（personal 模式等价），禁跑 open-ikc 仓库根 |
| 安装需要网络 | M0 走沙箱外批准 `npm install -g openwiki`；或 vendored node_modules |
| open-ikc 为占位实现 | 以 `AGENTS.md` + 代码为准，引擎保留其 DTO/envelope/稳定 ID 规则兼容 |
| visualizer 依赖 CDN | 引擎只消费 `graph.json` 数据，不依赖在线 viewer |

## 8. 后续演进（MVP 之后）

- Node bridge 替换 CLI 子进程适配，暴露 OpenWiki 程序化能力（模型、连接器、增量 diff）。
- `searchMode=page` + 沿 wiki-link 扩展候选（对接 P4 检索路由）。
- 多租户配额（页面数/文件大小/LLM 调用量）、wiki 版本快照与审计。
- `ingest` 连接器体系（git-repo/web-search/notion）面向企业知识源接入。
